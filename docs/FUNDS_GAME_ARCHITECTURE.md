# 资金游戏架构与开发准入

更新时间：2026-07-26

状态：架构规划，未经确认不扩写新游戏。

## 1. 产品定义

这里的“游戏”不是售票型休闲小游戏，而是：

- 用户使用平台星币参与；
- 多人实时对战，或捕鱼等持续消耗玩法；
- 每局、每桌或每个结算周期都有明确的投入、输赢和账单；
- 服务端权威判定，客户端只负责显示和发送操作；
- 每款游戏拥有独立主图、方形图标、加载图和桌面 UI，不允许共用占位主图。

`cmf_minigame` 只是上架目录，不是游戏架构本身。数据库加一行不能等同于“完成一款游戏”。

## 2. 上架硬门槛

一款游戏只有同时具备下列内容才能进入 `status=1`：

1. 玩法 PRD：人数、局流程、下注/消耗点、赔率或输赢算法、抽水、限额、超时和断线规则。
2. 资金模型：入局冻结、局中消耗、派彩、退款、异常补偿和对账方式。
3. 权威 Go 服务：随机、发牌、命中、动作校验、结算全部在服务端。
4. 幂等结算：每局、每次资金动作都有唯一业务单号，重复请求不能重复扣款或派彩。
5. 风控配置：单局限额、单日限额、异常胜率、设备/账号关联和人工冻结能力。
6. 完整素材：独立 4:3 主图、1:1 图标、横竖屏加载图、桌面背景和实际玩法 UI。
7. 测试报告：规则测试、资金守恒、断线重连、并发压测、故障恢复和安全测试。
8. 合规审核：许可证、素材版权，以及目标运营地区要求的审查。

缺一项即保持下架，前端不展示。

## 3. 服务边界

```text
UniApp
  -> Game Gateway（登录、启动凭证、版本、灰度）
  -> Matchmaker（匹配、桌号、座位、断线重连）
  -> 每款游戏的 Go 权威服务
  -> Wallet/Ledger（唯一资金写入口）
  -> MySQL 账本 + Outbox

Redis
  -> 在线状态、匹配队列、短期房间状态

MySQL
  -> 用户余额、冻结资金、局单、结算单、不可变流水、审计事件
```

- 游戏服务不能直接修改 `cmf_user.coin`。
- PHP、客户端和游戏房间都不能成为资金最终裁决者。
- Wallet/Ledger 是余额和流水的唯一写入口。
- 所有金额使用 `int64`，禁止浮点金额。
- 前端只展示服务端状态，不计算输赢结果。

## 4. 标准资金流程

### 棋牌/多人局

```text
进入匹配
  -> Wallet 冻结入局金
  -> 坐满并确认冻结成功
  -> 服务端开始对局
  -> 记录可重放的动作序列
  -> 生成唯一结算单
  -> Wallet 原子完成扣除、派彩、抽水和解冻
  -> 写流水与 Outbox
  -> 客户端收到最终账单
```

未坐满、开局失败、服务崩溃且无法恢复时，冻结资金必须自动解冻。

### 捕鱼

捕鱼不能每发一炮都跨服务同步写一次用户总余额，否则延迟和数据库压力不可控。

正确模型：

1. 用户进入桌时，从平台钱包冻结一笔游戏额度到该桌的托管余额。
2. 炮弹消耗和捕获奖励按严格递增序号写入游戏内资金事件日志。
3. 服务端定期做余额检查点，事件可重放、可校验、不可跳号。
4. 退出、断线超时或达到结算周期时，把净额通过唯一结算单原子写回平台账本。
5. 平台余额、桌内托管余额、累计消耗、累计奖励必须始终满足资金守恒。

## 5. 账本模型

建议由 Go Wallet/Ledger 服务管理：

- `wallet_account`：用户可用余额和冻结余额；
- `wallet_hold`：入局冻结，状态为 pending/committed/released；
- `game_round`：局号、桌号、游戏、参与者、开始/结束状态；
- `game_settlement`：唯一结算单和幂等键；
- `wallet_ledger_entry`：不可变借贷流水；
- `game_event_log`：局内权威事件序列与哈希；
- `outbox_event`：结算后可靠通知。

核心不变量：

- 同一结算单只能成功一次；
- 余额变化必须有对应流水；
- 一局内玩家净输赢 + 平台抽水 = 0；
- 捕鱼桌内托管余额变化 = 奖励 - 消耗；
- 任何重试、重连或服务重启都不能重复派彩。

## 6. 每款游戏的独立资产规范

每款游戏至少提交：

| 资产 | 比例 | 用途 |
| --- | --- | --- |
| 主图 | 4:3 | 大厅卡片和推荐位 |
| 图标 | 1:1 | 快捷入口和记录页 |
| 横屏加载图 | 16:9 | 棋牌、捕鱼进入页 |
| 竖屏加载图 | 9:16 | 竖屏玩法 |
| 桌面背景 | 实际游戏分辨率 | 对局场景 |

素材优先使用已授权资源；缺失时使用 GPT ImageGen 按单款游戏分别生成。禁止所有游戏共用一张图，禁止把占位图作为上架素材。

## 7. 开发顺序

1. 冻结新增游戏，只维护当前六款真实资金游戏。
2. 完成 Go Wallet/Ledger 的冻结、提交、释放和对账接口。
3. 抽出统一 Game SDK：启动验签、心跳、重连、局号、资金托管、结算和审计。
4. 先把捕鱼接入托管余额模型。
5. 再把斗地主、麻将、炸金花、跑得快、红中麻将接入统一局结算。
6. 对当前六款完成资金守恒测试和并发压测。
7. 由产品确认下一批玩法和资金模型后，再逐款开发、逐款生成独立素材、逐款上架。

在第 1–6 步验收前，不以“凑数量”为目标增加游戏。
